# Supabase + RLS Deep Dive for Vibe-Coded Apps

Supabase is the most common backend in Lovable / Bolt / Cursor-generated apps. Missing or weak Row Level Security is the single most frequent critical finding in public scans of these apps.

## Why RLS Matters

- The `anon` (publishable) key is meant to be in the browser.
- Without RLS, any visitor who has the key can read and often write your tables directly via the REST or realtime API.
- Scans keep finding user emails, payment status, API keys stored in tables, and full user records exposed this way.

## Non-Negotiable Rules

1. **Enable RLS on every table** that contains user data, personal data, or anything sensitive.
2. After enabling RLS, **no data is accessible** through the API with the anon key until you create policies. This is the safe default.
3. Policies must be **least privilege**. Prefer:
   - `auth.uid() = user_id` (or equivalent ownership check)
   - Role-based checks where needed
4. Never use overly broad policies such as:
   - `true`
   - `auth.uid() IS NOT NULL` (this only checks “logged in”, not ownership)
5. Test every policy as an unauthenticated user and as a different authenticated user.

## Recommended Policy Patterns

### Users can only read/update their own row
```sql
-- Enable RLS
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;

-- SELECT
CREATE POLICY "Users can view own profile"
ON profiles FOR SELECT
USING (auth.uid() = id);

-- UPDATE
CREATE POLICY "Users can update own profile"
ON profiles FOR UPDATE
USING (auth.uid() = id);
```

### Users can only access their own records in a related table
```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can view own orders"
ON orders FOR SELECT
USING (auth.uid() = user_id);

CREATE POLICY "Users can insert own orders"
ON orders FOR INSERT
WITH CHECK (auth.uid() = user_id);
```

### Public read, authenticated write (use sparingly)
Only for truly public content (e.g. published blog posts). Still scope carefully.

## Common Mistakes Generated by AI Tools

- Tables created without `ENABLE ROW LEVEL SECURITY`
- Policies that only check `auth.role() = 'authenticated'`
- Service-role key used in the client (never do this)
- Policies added only for some tables, leaving others open
- Realtime subscriptions without corresponding RLS

## Agent Instructions

When scaffolding any Supabase table or schema:

1. Always emit `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`
2. Generate restrictive ownership policies by default.
3. Explicitly comment that the policies must be tested with the anon key.
4. Never put the `service_role` key in frontend code or environment variables that reach the browser.
5. If the user asks for “make it work fast” in a way that disables RLS, refuse and explain the exposure.

## Quick Verification

From a browser console or API client using only the anon key and no auth header:

- Can you `SELECT *` from the table?
- Can you insert or update another user’s row?

If yes → the app is not ready for production.
